Convolution is an array operation where each output data element is a weighted sum of a collection
of neighboring input elements. The weights are provided via an input array that we will call the
convolution filter. Implement a CUDA kernel to compute 3D convolution for each element of an
input 3D array by averaging the values of its neighboring elements keeping the element under
consideration at the center.
• Use single-precision floating point type.
• Assume that the sides in 3D arrays have the same dimensions and are a multiple of eight.
• The convolution filter is a 3D cube with dimensions K × K × K, where K = 5. The filter is
initialized in the template file.
• Assume the missing boundary elements (i.e., ghost cells) are zero.
• The output array has the same dimensions N × N × N as the input array, where N ∈
{64, 128, 256}.
• Implement a single-threaded CPU convolution and assert that the your CPU and GPU results
are same (a helper function is included in the template file).
Implement two versions of the 3D kernel. The first one should be a basic version that uses
global memory while the second one is your optimized version that implements (a) tiling using
shared memory, (b) constant memory for the filter, and (c) loop unrolling. Compare and report
the performances both end-to-end and just the kernels. It is always a good practice to take the
average of multiple runs.

Problem 3

[30 + 30 + 5 + 20 marks]

A Bloom filter is a probabilistic data structure used to efficiently test whether an element is a
member of a set. It uses a bitmap (bit array) and multiple (say k) hash functions to represent
the inserted elements. While inserting a key x, the k hash functions are evaluated with x, and
the corresponding bit positions in the bitmap are set. A lookup for key y proceeds similarly, and
returns “present” only if all the hashed locations are set. The key is not stored in the filter.
A Bloom filter has no false negatives: if it reports that a key is absent, then the key is guaranteed
to not be in the set. It is obvious that a vanilla Bloom filter can generate false positives. That
is, the Bloom filter may report that a key exists even though the key was never inserted. The
advantage of a Bloom filter is that it provides fast insertion and lookup operations while using
relatively little memory.
The above design cannot support deletion because resetting a bit in the bitmap from 1 to 0
may affect the correctness for other keys that hash to the same location. You have to design a
“counting Bloom filter” that supports deletion by instead maintaining counters. For a counting
Bloom filter, each position contains a counter instead of a single bit.
(i) Implement the three data structure operations, insert(), delete(), and search() as separate kernels. Each kernel will take a batch of keys to be operated on. The three kernels
will be invoked separately from the host code, e.g., insert() followed by search() followed
by delete() and again followed by search(). That is, an insert(x) cannot overlap with
a delete(y). This constraint helps in checking the correctness of your implementations.
(ii) Implement a “blocked” variant for the counting Bloom filter. The blocked version will use
k + 1 hash functions. On an input x, the first hash function will select a GPU L1 cache
block, and the next k hash functions will operate in the given block. This improves localtiy,
but increases the rate of false positives.
(iii) Write a test routine check_result() on the host that will validate the correctness of
your GPU kernels. A simple idea is to perform the same operations on a std::set or
std::unordered_map on the host and check for equivalence with the GPU Bloom filter
data. Include the test routine in your submission.
This also allows you to (imperfectly) test for false positives for search operations. Report
the false positive rate (ratio of false searches over all searches) for the two variants, given an
input trace.
(iv) Profile your insert() and search() kernels (ignore delete()) with NVIDIA Nsight Compute, and report the following metrics as output by the profiler: memory bandwidth utilization, arithmetic intensity, achieved occupancy, warp efficiency, L2 cache hits, and long
scoreboard stalls. List the top three performance bottlenecks listed by the profiler (e.g., uncoalesced memory access, short or long scoreboard stalls, and atomics) in your PDF report.
